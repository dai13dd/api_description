02 / Detailed Architecture

サーバーレス Web API 詳細アーキテクチャ

図中の各コンポーネントをクリックして詳細表示

Amazon API Gateway の役割

クライアントからのHTTPSリクエストを受け付け、URLパスやHTTPメソッドに応じて適切なLambda関数へ振り分けます。認証・認可やアクセス制限（スロットリング）も入口で一括制御します。

開発メンバーの負荷が減るポイント

Nginxの設定ファイル管理やSSL証明書の更新作業が不要になります。認証やCORS設定も共通化できるため、各API側での重複実装が減ります。

03 / Developer Experience

開発メンバーの負荷がどう減るか（Before / After）

やらなくてよくなる 4 つの面倒ごと

1. サーバー・インフラ管理

Before OSアップデート、Nginx設定、ディスク容量監視が必須
After すべてゼロ。AWSに任せてコードだけ書く

2. デプロイの衝突・影響範囲

Before 同一サーバー上の他メンバーの修正で自分のAPIが止まるリスク
After 関数単位で独立デプロイ。他APIへの影響ゼロ

3. 障害対応・再起動

Before プロセス落ちの手動復旧、急負荷時の夜間スペック対応
After 自動スケール＆リクエスト毎の独立実行で復旧作業から解放

4. 学習・環境構築コスト

Before 基盤に合わせて言語統一や複雑なフレームワーク設定が必要
After 自分の得意言語（Python / C#）で単一関数を書くだけ

「インフラを動かすための雑務」を手放し、本来やりたかった業務ロジック実装に集中できます。

06 / Code Comparison

実装イメージ：入力を受け取り、JSONを返すだけ

lambda_function.py（Python 3.x / 型ヒント付き） 
import json
from typing import Any

def lambda_handler(event: dict[str, Any], context: Any) -> dict[str, Any]:
    # クエリパラメータを取得（例: GET /hello?name=DevTeam）
    params = event.get("queryStringParameters") or {}
    name = params.get("name", "World")

    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps({"message": f"Hello, {name}!"}, ensure_ascii=False),
    }

フレームワークの複雑な設定なし！ 入力（event）を受け取って出力（JSON）を返すだけでHTTPS APIとして公開されます。

Function.cs（C# .NET） 
using System.Text.Json;
using Amazon.Lambda.APIGatewayEvents;
using Amazon.Lambda.Core;

public class Function
{
    public APIGatewayProxyResponse FunctionHandler(
        APIGatewayProxyRequest request, ILambdaContext context)
    {
        var name = request.QueryStringParameters?.GetValueOrDefault("name") ?? "World";

        return new APIGatewayProxyResponse
        {
            StatusCode = 200,
            Headers = new Dictionary<string, string> { ["Content-Type"] = "application/json" },
            Body = JsonSerializer.Serialize(new { message = $"Hello, {name}!" })
        };
    }
}

サーバー起動コード不要！ リクエスト（APIGatewayProxyRequest）を受け取り、レスポンスを返すだけで完結します。

07 / Constraints & Solutions

実務で知っておくべき 3 つの制約と対策

仕組み上のルールを最初に押さえておけば、設計時に迷うことはありません。

1. タイムアウト上限

API Gateway 最大29秒 / Lambda 最大15分

同期APIレスポンスは29秒以内に返す必要があります。対策：重い集計やファイル生成などの長時間処理は、SQS等を挟んで非同期処理に切り出します。

2. コールドスタート（初回起動時のわずかな遅延）

数百ms〜数秒

アクセスがない状態からの初回呼び出し時のみ起動時間がかかります。対策：社内ツールなら実用上許容範囲。シビアなAPIのみ Provisioned Concurrency で常時待機させます。

3. ステートレス設計（ローカル永続保存不可）

実行環境は使い捨て

コンテナは処理後に破棄されるため、ローカルディスクやメモリにデータを保持できません。対策：ファイルは Amazon S3、状態やデータは RDS / DynamoDB へ保存します。

08 / Coexistence & Summary

使い分けの目安とまとめ：EC2 との共存戦略

Recommended

Lambda + API Gateway が向くケース

  • 軽量な CRUD API・独立したマイクロサービス
  • バッチ連携・外部サービスからの Webhook 受信
  • 不定期アクセスの社内ツール（夜間・休日0円）
  • Python / C# メンバーによる小規模APIの素早い量産

Keep on EC2

EC2 + FastAPI を残すべきケース

  • 24時間コンスタントに高トラフィックが続くAPI
  • WebSocket や長時間コネクション維持が必要な処理
  • 重い機械学習（ML）モデルの常駐メモリ利用
